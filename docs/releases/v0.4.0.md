whichphp v0.4.0 adds CycloneDX output, a diff mode for "did the rebuild fix it?", and the base image an app image was built on. Cluster mode reads `php.ini` from ConfigMaps and says how long a workload has run vulnerable PHP. GetPageSpeed, CloudLinux's own PHP and TuxCare's Alpine builds join the packager data. Some verdicts for those packagers' builds change; see [Verdicts that change](#verdicts-that-change). The GitHub Action works the same as in v0.3.0.

### What's new

- **CycloneDX output.** `whichphp image -o cyclonedx[=file]` writes a CycloneDX 1.6 BOM with the PHP builds as components and a VEX analysis per CVE. It follows the same evidence rules as OpenVEX: `resolved` and `not_affected` only on positive evidence, `exploitable` for vulnerable builds, `in_triage` for everything else. Unlike OpenVEX it also works for directories and archives without a tag. `--vex-author` names the BOM's author.
- **`whichphp diff <before> <after>`** compares two images, or two reports from `whichphp image -o json`: which PHP builds were added, removed or changed, every verdict before and after, `session.upload_progress.enabled`, and a one-line result such as "Fixed by this change" or "Got worse". It says fixed only on proof: an after image with no PHP found, or one fixed only by a distro backport whose feed coverage wasn't confirmed, isn't called fixed. The exit code is the after image's, as `whichphp image` would give it. `-o json` for scripts.
- **Which image to rebuild on.** An image built on an official `php` image inherits its environment, so the report now names the base (`Base: php:8.4.26-apache-trixie`) and, when that PHP is still in the image and vulnerable, the floating `php` tag to rebuild on (such as `php:8.4-apache`), or that the branch gets no fix. Bitnami's `php-fpm` images are recognized too. No registry is asked.
- **Cluster mode:**
  - **`php.ini` from ConfigMaps.** ConfigMaps mounted at PHP configuration paths are read with `kubectl get configmap` and applied the way Kubernetes mounts them (`subPath`, directory mounts, `items`, `optional`), so `session.upload_progress.enabled` per workload reflects them. A file from a ConfigMap counts only where the image's own PHP reads its configuration. A ConfigMap that can't be read, Secrets, other volumes, `PHP_INI_SCAN_DIR` and `PHPRC` (from `env`, the command line, or an `envFrom` ConfigMap, which is read for them, or Secret, which isn't), and PHP's own options in the container's command line that change its settings are named but not followed, and since they could turn the setting back on, an `off` becomes `unknown`.
  - **How long a workload has run vulnerable PHP**, from its pods' start times: "running vulnerable PHP since Oct 12, 2026, 20 days".
  - **`--from-docker`** reads the running images from the local Docker daemon (Docker Desktop's Kubernetes, or minikube with its Docker runtime) instead of the registry; it only runs `docker version` and `docker image inspect`, and falls back to the registry when Syft reads another architecture than the node's. kind isn't covered.
- **A cut-off download is retried once.** When Syft's download of an image ends with `unexpected EOF`, a reset connection or a timeout, the scan runs once more and the report says so. Archives and directories on disk aren't read twice. This helps `whichphp image`, `cluster` and `index`.
- **More packager data:**
  - **GetPageSpeed:** 25 rows from its own advisory GPSA-2026-0001, for its base packages and Software Collections on EL7, EL6, Amazon Linux 2 and EL9. Each row applies only to builds of its own distro release, because GetPageSpeed numbers them apart.
  - **CloudLinux's own system PHP** on CloudLinux 8, 9 and 10.
  - **TuxCare on Alpine:** php82 on Alpine 3.18, and alt-php 7.3 to 8.1 on Alpine 3.23 and 3.24, with an apk version order ported from apk-tools.

  Every new row was checked a second time against the packager's own repository metadata, errata or VEX files.

### Verdicts that change

- **GetPageSpeed builds** of PHP 5.4 to 8.1 read `FIXED_BY_VENDOR_BACKPORT` from the advisory's first fixed release on, and `VULNERABLE` below it, instead of `NEEDS_VENDOR_CONFIRMATION`. Early fixed builds whose rpm Vendor tag is empty can't be told from the distro's and aren't credited.
- **CloudLinux's system PHP** and **TuxCare's Alpine builds** listed above read `FIXED_BY_VENDOR_BACKPORT` or `VULNERABLE` instead of `NEEDS_VENDOR_CONFIRMATION`.
- **Cluster mode:** a workload whose ConfigMap turns `session.upload_progress.enabled` off now reads off, which changes the result of `--fail-on-mitigation`.

### Limits

- For TuxCare and CloudLinux's system PHP, only the distro builds in the table are known; a later rebuild on another distro build reads `NEEDS_VENDOR_CONFIRMATION` until the table lists it.
- alt-php on Alpine 3.22 has no data yet.
- The base image is reconstructed from the environment and the distro: `cli` and `zts` images show no variant, and an image that replaced the base's PHP is judged by its own PHP, without advice.
- cPanel's ea-php73 and older still read `VULNERABLE_EOL`: cPanel hasn't shipped their fixes as of November 1.

```sh
sha256sum --ignore-missing -c SHA256SUMS        # on macOS: shasum -a 256 --ignore-missing -c SHA256SUMS
gh attestation verify whichphp_0.4.0_linux_amd64.tar.gz --repo yusufyildiz34/whichphp \
  --signer-workflow yusufyildiz34/whichphp/.github/workflows/release.yml --bundle whichphp_0.4.0.sigstore.json
```
